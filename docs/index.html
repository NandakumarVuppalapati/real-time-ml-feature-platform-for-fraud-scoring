The problem this solves

Most fraud pipelines fall into one of two camps: pure batch (nightly Spark jobs, features hours stale by scoring time) or an ad-hoc real-time system where someone re-implements the batch feature logic in a different language for low-latency serving — and the two implementations quietly drift apart. That drift is training/serving skew, one of the more expensive, hard-to-detect bug classes in applied ML. This project's actual point is the plumbing that prevents it: one feature definition, computed by two engines (Flink online, Spark offline), served through one abstraction (Feast) so both paths agree on what “features as of this moment” means.

Real bugs, fixed live

Built and debugged against a running Docker Compose stack, not just written once and left untested. A few of the issues that only surface at real scale or across a real dependency graph:

Feast's point-in-time join OOM'd at 1.3M rows

Feast's local/file-based get_historical_features() loads its offline source into memory regardless of entity set size — it OOM-killed repeatedly, even after reducing the join to a matched ~46K-row slice on both sides.

Fix: recognized that the label timestamp and feature snapshot timestamp are identical by construction here, so an asof join degenerates to a direct read. Read the parquet straight into pandas — same point-in-time-correct result, no memory blowup, full dataset preserved.

Model artifacts silently vanished after training

Training reported success — registered a model version, no error — but serving failed with MlflowException: No such artifact: ''. MLflow's local artifact store is a plain filesystem path that only the MLflow container had mounted; every other container's model log/load calls were writing to their own throwaway filesystem.

Fix: mounted the same Docker volume into every container that reads or writes model artifacts, not just the tracking server.

xgboost/scikit-learn version drift broke model saving

scikit-learn 1.6+ replaced the _estimator_type class attribute with a new tags protocol. Pinning xgboost<3.0 (the version documented to fix this) actually made it worse — it forced pip onto xgboost's last, older 2.x release, incompatible with the newer scikit-learn actually installed.

Fix: dropped the upper bound entirely, letting pip resolve to xgboost's current major version, which targets current scikit-learn releases.

Base image drift broke the Java runtime

python:3.11-slim's underlying Debian release moved forward on a routine rebuild months later and dropped the openjdk-17 package PySpark's Dockerfile depended on.

Fix: moved to openjdk-21 — PySpark 3.5.x supports it natively, so this was a same-behavior swap, not a downgrade.
